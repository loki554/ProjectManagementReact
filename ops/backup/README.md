# Бэкапы базы

Сервис `backup` из `docker-compose.prod.yml` (см. 8.5 в `IMPROVEMENTS.md`).
Раз в сутки в `BACKUP_AT` снимает `pg_dump -Fc`, **проверяет дамп восстановлением**
во временную базу и удаляет дампы старше `BACKUP_RETENTION_DAYS`.

## Что где

| Файл | Что делает |
|---|---|
| `scheduler.sh` | точка входа контейнера: стартовый прогон + ожидание `BACKUP_AT` |
| `backup.sh` | один цикл: снять дамп → проверить → почистить просроченные |
| `verify-restore.sh` | восстановить дамп во временную базу и убедиться, что данные на месте |

Каждый из трёх запускается и руками:

```bash
C="docker compose --env-file .env.prod -f docker-compose.prod.yml"

$C exec backup bash /ops/backup.sh                                  # снять дамп прямо сейчас
$C exec backup bash /ops/verify-restore.sh /backups/pmtracker-….dump # проверить конкретный файл
$C exec backup ls -lh /backups                                  # что вообще есть
```

> Из Git Bash на Windows абсолютные пути внутри контейнера надо защищать от подстановки:
> `MSYS_NO_PATHCONV=1 $C exec backup bash /ops/backup.sh`. Иначе `/ops/backup.sh`
> превратится в `C:/Program Files/Git/ops/backup.sh` ещё до того, как доедет до докера.

## Восстановление

Порядок именно такой: **сначала останавливаем приложение**. Восстановление в базу,
с которой работает живой бэкенд, даёт не восстановленную базу, а смесь.

```bash
C="docker compose --env-file .env.prod -f docker-compose.prod.yml"

# 1. Остановить бэкенд (Postgres оставить)
$C stop backend

# 2. Убедиться, что дамп цел — той же проверкой, что ходит по расписанию
$C exec backup bash /ops/verify-restore.sh /backups/pmtracker-20260918T033000Z.dump

# 3. Пересоздать базу и залить дамп.
#    --clean --if-exists вместо dropdb: дропнуть базу, к которой кто-то подключён, нельзя,
#    а так объекты пересоздаются внутри существующей.
$C exec backup pg_restore --dbname="$DB_NAME" --clean --if-exists --no-owner \
    --no-privileges --exit-on-error /backups/pmtracker-20260918T033000Z.dump

# 4. Поднять бэкенд. Flyway увидит схему на нужной версии и ничего не тронет
#    (ddl-auto: validate, миграции уже внутри дампа).
$C start backend
```

Если дамп старше текущей версии кода, Flyway доложит недостающие миграции сам — это
штатный путь. Обратное (дамп **новее** кода) Flyway не умеет и упадёт на валидации;
тогда сначала выкатывается соответствующая версия приложения.

## Чего эта схема не делает

- **Это не офсайт-бэкап.** Дампы лежат в volume на том же хосте, что и база: пожар,
  украденный сервер или отказавший диск уносят и то, и другое. Том `backups` нужно
  синхронизировать наружу (`restic`/`rclone`/`aws s3 sync` по расписанию хоста) —
  внутрь compose это не зашито намеренно, потому что выбор хранилища и его ключи
  зависят от площадки.
- **Это не point-in-time recovery.** Дневной дамп означает «потеряем до суток». PITR
  (`archive_mode` + WAL-архив, `pgBackRest`/`wal-g`) — другая задача и другой объём работы;
  заводить её стоит, когда «до суток» станет неприемлемым ответом.
- **Файлы вложений сюда не входят.** В дампе только база; вложения и аватарки лежат в
  volume `storage` (или в S3, если включён `STORAGE_TYPE=s3`). Восстановленная база со
  ссылками на исчезнувшие файлы — это половина восстановления.

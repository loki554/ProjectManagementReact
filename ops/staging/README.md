# Стенд (staging)

Накладка на прод-стек, а не отдельный стек: `docker-compose.staging.yml` описывает только
отличия и применяется поверх `docker-compose.prod.yml`. Смысл в том, чтобы стенд проверял
ровно то, что поедет в прод, — отдельный самостоятельный файл разошёлся бы с прод-стеком
с первой же правки. См. 8.9 в `IMPROVEMENTS.md`.

## Запуск

```bash
cp .env.staging.example .env.staging     # и заполнить
docker run --rm httpd:2-alpine htpasswd -nbB staging '<пароль>' > ops/staging/htpasswd

docker compose --env-file .env.staging \
  -f docker-compose.prod.yml -f docker-compose.staging.yml up -d --build
```

`htpasswd` в git не попадает (закрыт `.gitignore`) и генерируется на месте. Файл нужен
до первого `up`: без него nginx не стартует — `auth_basic_user_file` указывает в пустоту.

Порядок `-f` важен: второй файл накладывается на первый. Поменяв их местами, получите
прод-стек с прод-почтой под именем стенда.

## Чем стенд отличается от прода

| Отличие | Зачем |
|---|---|
| Почта уходит в MailHog | на стенде живут копии реальных адресов, и письмо «подтвердите регистрацию», ушедшее живому человеку, стоит дороже всей экономии на настройке |
| `X-Robots-Tag: noindex` на каждом ответе | иначе поисковик найдёт стенд (по ссылке из письма, по записи в Certificate Transparency) и выдаст тестовые данные по запросу с названием продукта. `robots.txt` этого не делает: он просит не сканировать, но уже попавшую в индекс страницу не убирает |
| Basic-auth на весь стенд, включая `/api/` | забор от случайных посетителей. Закрытая страница при открытом API — это не закрытый стенд |
| Rate limiting выключен | половина ручных проверок — это вход-выход по кругу, а на шестой попытке стенд отвечал бы 429 |
| Swagger UI включён | стенд закрыт паролем, а карта API — это то, ради чего на него и ходят |
| Ротация бэкапов 3 дня вместо 14 | данные тестовые, а процедуру восстановления проверять всё равно надо где-то — и лучше здесь, чем впервые в проде |

Spring-профиль остаётся `prod`. Профиль `staging` завёл бы ещё одну конфигурацию, которую
никто не проверяет: стенду нужны не другие настройки, а другие **значения** — другая база,
другой домен, другой SMTP, — и они приходят из `.env.staging`.

## Что проверить на стенде перед выкатом

Порядок не случайный: сверху то, что ломается чаще и заметнее.

1. Регистрация до конца — письмо видно в MailHog (`http://<стенд>:8025`), ссылка из письма
   открывается, вход работает. Это проверяет сразу SMTP, `FRONTEND_BASE_URL` и то, что
   ссылки ведут на домен стенда, а не на прод.
2. Живые обновления: открыть проект в двух вкладках, поменять задачу в одной. Это ловит
   буферизацию SSE на прокси — единственную вещь, которая ломается только за nginx и никак
   не проявляется в dev.
3. Загрузка вложения крупнее мегабайта — `client_max_body_size` (дефолт nginx отрезал бы
   на 413).
4. `docker compose ... exec backup bash /ops/backup.sh` — дамп снимается и проходит
   проверку восстановлением на тех же правах и путях, что будут в проде.

## Обновление стенда до состояния прода

Данные стенда — тестовые, и восстанавливать их неоткуда, кроме прода. Перенос делается
дампом (`ops/backup/README.md`), и **до** заливки в стенд из копии нужно убрать или
обезличить почтовые адреса: иначе первый же фоновый прогон уведомлений отправит письма
реальным людям. MailHog это перехватит, пока перенаправление почты на месте, — но
полагаться на одну строчку конфигурации в этом вопросе не стоит.
